# 代码规范

适用于 packages、extensions 中的生产源码和长期维护脚本。目标是对外易用易学、内部职责明确、协议行为可验证。内部复杂度可为稳定的模型化与链式体验服务，不以文件数、函数数或代码行数衡量设计质量。

## 一、书写规范

### 排版与命名

- UTF-8、LF、两个空格缩进、文件末尾换行、无行尾空白，遵循根 .editorconfig。
- TypeScript 使用分号、单引号；多行结构保留尾逗号，建议打印宽度 100。分支、循环及多语句函数分行书写，不堆成手写单行代码。
- 格式归一由仓库统一工具和配置执行，不逐行手调，也不因小改格式化无关文件。格式化工具必须先落地到依赖、配置和命令，再宣称检查已执行；.editorconfig 不等于完整 TS 格式检查。
- 值、函数、字段使用 camelCase，类型、接口、类使用 PascalCase；文件与目录使用 kebab-case，包名小写。类型名不增加无意义的 I/T 前缀，泛型优先使用 TModel、TOperation 等有含义的名称。
- 资源 operation 使用 list/get/post/put/patch/delete，HTTP method 使用大写。scheme、transport、preset、definition、reference、request、response 各指各自概念，不混用 model/service/provider 作为任意容器名称。
- 注释和维护说明以中文为主，代码标识符使用英文；外部协议字段保留其标准名称。维护已有英文注释时可以随相邻语义改动逐步统一，不机械整库翻译。

### 类型与导出

- 使用 ESM、具名导出和 `import type`；NodeNext 的包内相对 TS 导入写编译后 `.js` 扩展名。
- 公共类型从包公开入口提供，不依赖全局 .d.ts 注入、不让消费者导入 src。
- 边界未知值为 unknown，经过解析再收窄；禁止用 any、双重断言或非空断言代替校验。必须存在的适配断言限定最小范围并说明依据。
- 保留 strict、noUncheckedIndexedAccess、exactOptionalPropertyTypes。缺失与显式 undefined 的差异按契约处理，不能为通过编译关闭检查。
- 调用者拥有的声明、请求设置与运行时服务实例分别处理。只在承诺边界做快照/冻结，不对 Transport、AbortSignal 或第三方实例盲目深拷贝/深冻结。
- 公共输入字段使用只读类型表达归属；内部局部可变变量服务明确算法，不把 readonly 当运行时不可变证明。
- 导出项只包含真实公共用途；内部解析辅助函数不因为测试便利随意进入 exports。

### 注释

生产模块顶部说明职责、在流程中的位置及主要导出。纯转出 index 可以用一句职责说明，不复制所有实现注释。

公开函数/方法说明输入、返回、副作用与可能异常，多参数分别说明。公开类型字段说明含义、约束和缺省；使用 JSDoc 的 @param、@returns、@throws 等表达，不让独立文档替代源码必要说明。

```ts
/**
 * 将资源操作声明归一化；不执行 HTTP 请求。
 * @param config 资源形态、预设与本层能力声明；缺省不开放操作。
 * @returns 不可变的资源定义。
 * @throws ResourceConfigurationError 配置无效或预设继承循环时抛出。
 */
```

非显然逻辑解释原因：星号为何延迟到资源形态确定后展开、false 的优先级、身份 0 的处理、编码和取消边界等。普通赋值不写逐行复述。不可达约束需要说明依据，TODO 必须有明确问题，不用 TODO 代替错误处理。

### 错误与异步

- 无效配置和不支持操作在副作用前拒绝，错误指出真实阶段和原因。
- 用 Error 子类及稳定分类，不抛字符串，不用布尔 handled 标志把恢复和继续抛错混为一谈。
- 保留 cause 和必要请求/响应信息；公开日志或错误输出对 token、Cookie、密码及请求体敏感字段脱敏。
- 不吞错或 catch 后再次构造误导性原因；仅为原样 throw 的 try/catch 应去除，确有清理、分类或补充上下文再捕获。
- Promise 必须传播、等待或显式拥有其后台生命周期。超时、取消等待和终止实际请求分别定义；不把 Promise.race 当底层取消证据。
- 同步声明 API 不接受伪装同步的异步结果。可选观测失败不得导致业务请求重发。

## 二、代码组织规范

### 分层与职责

主包拥有资源声明、操作能力、RESTful 推导、scheme、链式上下文及公共扩展契约。Axios、Mock、缓存、Pinia 等能力属于扩展；不能通过静态导入或类型泄漏变成主包必需依赖。

scheme 决定已有能力如何适配 HTTP，不为资源增加能力。HTTP Mock 匹配最终 HTTP 请求，不复制另一套按资源操作直接返回业务值的执行器。缓存只管理本库定义的缓存结构，不成为任意 Store 访问器。

入口装配、配置解析、能力解析、请求构造、执行、响应适配、结果建模保持可追踪的阶段与错误归属。阶段不强制各建一个类或包；复杂算法保留在能够完整阅读的职责单元内。

### 声明与执行的唯一来源

稳定可枚举的操作、目标位置、默认方法及适用规则优先使用集中类型化目录，实际驱动校验、星号、匹配、分发和公共类型。不要在文档清单、解析器和执行器各复制一份默认全集。

同类变体通过明确参数或注册项复用共同规则，不复制文件改名称，不在默认分发之外保留另一条特殊执行路径。时序、递归和单条件算法可以过程式表达；不把所有 if/switch 都改成注册表。

### 模块与函数

- 模块按职责拆分，不按函数个数拆分。内部复杂性不能泄漏为消费者必须逐接口填写的配置。
- 顶层入口只装配和转出；跨模块内部依赖指向实际所有者，不绕聚合 index 引入循环。
- 继承、函数、组合、Proxy 均可使用；不能通过 prototype 借用或类型断言掩盖真实职责依赖。Proxy 必须保持已承诺的键枚举、序列化与字段冲突规则。
- 链式状态与单次请求隔离；公共定义可复用，请求身份、查询、signal 与响应状态不放在跨调用共享可变对象中。
- 配置只按已知 schema 合并；数组、函数、false、undefined 和模式切换有明确策略。不对全部配置使用无限制深合并。
- 安全校验、编码、规范化不能重复或互相抵消。动态属性按自有键验证，防止原型键变成操作或资源。

### 包与依赖

跨包只使用 manifest 声明的公开入口，不跨包相对导入源码、不借其他项目 node_modules。聚合入口转出同一实现，不复制运行时。具体扩展即使同作者同仓库，也按公开契约接入，独立声明兼容范围。

新增底层包应有独立消费者、稳定职责和真实运行能力；否则先用模块或子入口。没有明确功能需要不提前创建 http/shared/utils 等包。不因整理规范安装 lodash、Mock.js 或其他运行依赖。

公共包支持的环境由实际 exports、源码和依赖闭包证明，不把仓库 Node 开发版本当浏览器或所有运行时支持声明。

### 测试组织

行为测试验证契约、边界和实际结果，不复制实现或仅断言某函数被调用。类型正反例与运行时校验分别维护；@ts-expect-error 标明拒绝原因，不使用 @ts-ignore 掩盖问题。

生产源码遵守完整自述及注释规则；长期脚本有文件头与关键函数说明。测试、fixtures、临时探针不强制逐函数 JSDoc 或生产文件头，不为注释和格式统一重写无关测试。可读性、合法语法和安全边界仍适用。

## 三、文件组织规范

```text
RESTModel/
  packages/<name>/
    src/index.ts          # 公共导出
    src/<domain>/         # 该包拥有的领域，规模需要时建立
    tests/                # 行为、类型、集成测试与必要 fixtures
    README.md
    package.json
    tsconfig.json
  extensions/<name>/      # 与包相同的内部结构，独立版本与兼容声明
  docs/
    README.md             # 分类索引
    *.md                  # 正式规范与参考
    design/               # 提案与设计比较
    maintenance/          # 状态、计划、长期审查与发布记录
  development/            # 有实际需要再建的长期工具
  pnpm-workspace.yaml
  tsconfig.base.json
```

生产源码、测试、文档和构建产物各有归属，不在 src 放临时日志、一次性报告或测试探针。每个包拥有自己的 dist，生成物不手工修改；根输出不能冒充包导出。

小领域可以先使用具名文件；同一目录出现不同阶段或多类职责时按领域分组，例如 operations/catalog.ts、operations/resolve.ts、resource/define.ts。类型跟随领域所有者，领域过大才增加 types.ts；错误跟随拥有者，跨域公共错误才集中。不要机械把每个 type/function 拆成文件。

index.ts 用于公共导出或清楚的领域装配，不积累业务逻辑。避免 generic helpers.ts、common.ts、utils.ts 持续接收无关实现；通用函数先寻找真实所有者。

源码文件名以职责命名，如 resolve-operations.ts；测试使用 *.test.mjs，类型用例使用 *.types.ts，与当前项目工具一致。新增测试域可以建 tests/<domain>，入口 glob 必须同步覆盖，不留下未执行的目录。

移动文件同步 import、exports、编译入口、测试、文档链接与发布白名单。不能为目录整齐移动无关文件或提前建设空层级。

## 规范适用与检查

规范是持续维护基准，不等同于现有源码已全量通过审查。修改时按影响范围落实；需要机械格式化或结构迁移时单独控制范围，不夹带行为修改。

代码检查按 [审查规范](code-review-standard.md)，文档同步按 [文档规范](documentation-standard.md)。工具接入与既有差距在维护资料中跟踪，不在规范中写进度。
